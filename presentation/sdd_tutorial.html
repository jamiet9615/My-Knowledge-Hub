解構 IEEE Std 1016
軟體設計描述 (SDD)

打造系統藍圖的邏輯、視圖與黃金原則 ✏️
受眾對象： 課堂老師與同學們
核心主題： 軟體需求轉譯、設計實體 10 大屬性、4 大設計視圖
實務案例： 《K33p_1t_s1mpl3》文字解謎 RPG 專題對照
參考標準： IEEE Std 1016-1998 / 1016-2009 國際規範
CHAPTER 01 :: 核心出發點

🌱 為什麼需要寫 SDD？從 What 走進 How

📋
SRS (需求規格書)
描述「系統該做什麼」(What)。
列出功能需求（F-01）、非功能品質（NF-01），這是給客戶與使用者的承諾。
🌉
SDD (設計描述書)
橋接架構「系統如何建構」(How)！
把需求轉譯成元件模組、資料字典、狀態機與演算法，是工程師的施工藍圖。
💻
Code (程式實作)
最終交付「具體運行的軟體」。
若沒有 SDD 直接寫 Code，容易陷入隨意拼裝、模組耦合、除錯與維護的災難。
💡 一句話總結 SDD 的價值：
「好的 SDD 讓不同的工程師看著同一份藍圖，能蓋出穩固、可獨立測試且能與 SRS 雙向對齊的軟體大廈。」
CHAPTER 02 :: 基本單位

🧱 SDD 的靈魂：設計實體 (Design Entity)

🧩
什麼是設計實體？
依據 IEEE 1016 定義，設計實體 (Design Entity) 是系統經由需求分解後的獨立元件：
  • 具有獨立結構與功能，能被單獨命名與參照。
  • 實體型態多樣：可以是一個子系統、前端模組、類別 (Class)、演算法程序，或一個資料庫 (Data Store)。
  • 目標：讓每一塊積木都能獨立實作、獨立測試、獨立置換（高內聚、低耦合）。
📐
資訊模型 (Information Model)
IEEE 1016 認為軟體設計本質上就是一套實體-屬性 (Entity-Attribute) 模型：
  • 系統由多個設計實體組成。
  • 每個實體透過一組標準屬性 (Attributes) 來回答：「它是誰？」、「它做什麼？」、「它依賴誰？」與「如何操作它？」。
  • 當所有實體的屬性都被清楚描述時，這份 SDD 即達到結構完備。
CHAPTER 03 :: IEEE 1016-1998

✨ 設計實體的 10 大黃金屬性 (Attributes)

標準規定每份完整的 SDD 必須回答關於設計實體的 10 個核心問題：
1. 識別 (Identification)
唯一的名稱與識別代碼，全局不可重複。
2. 類型 (Type)
實體性質（如模組、狀態機、資料儲存、類別）。
3. 目的 (Purpose)
為何存在？對應 SRS 的哪一項需求。
4. 功能 (Function)
它做什麼轉譯？輸入進來後輸出什麼。
5. 從屬 (Subordinates)
它包含哪些子元件？（Composed of 關係）。
6. 相依 (Dependencies)
它依賴或呼叫誰？（Uses 先後序關係）。
7. 介面 (Interface)
外部如何與它互動？方法、參數格式與錯誤碼。
8. 資源 (Resources)
所需的外部硬體、記憶體、LocalStorage 或 API。
9. 處理邏輯 (Processing)
內部演算法、邏輯分支、正規比對與防呆。
10. 資料 (Data)：實體內部的資料結構、儲存格式、型態限制與預設值（例如 GameState JSON）。
CHAPTER 04 :: 核心方法論

👓 四大經典設計視圖 (Design Views)

沒有人能用單一眼光看透整個系統！IEEE 1016 將 10 大屬性切分成四大專屬視圖：
🗂️
分解視圖 (Decomposition View)
關注重點：系統層級劃分與模組清單。
涵蓋屬性：識別、類型、目的、功能、從屬。
適合讀者：專案經理、系統架構師、新進成員。
🔗
相依視圖 (Dependency View)
關注重點：模組之間的呼叫關係、執行順序與資源依賴。
涵蓋屬性：識別、類型、相依性、資源。
適合讀者：架構評審、系統整合人員、測試規劃者。
🔌
介面視圖 (Interface View)
關注重點：外部如何呼叫、參數協定、通訊格式與錯誤回饋。
涵蓋屬性：識別、功能、介面規格。
適合讀者：協同開發組員（前後端對接、模組整合）。
⚙️
詳細設計視圖 (Detail Design View)
關注重點：演算法步驟、資料字典、正規表達式與例外保護。
涵蓋屬性：識別、處理邏輯 (Processing)、資料 (Data)。
適合讀者：具體負責撰寫程式碼的工程師。
CHAPTER 05 :: 標準演進

🚀 現代演進：IEEE 1016-2009 與架構視點

🏛️
全面對齊 ISO/IEC 42010
2009 年版本進行了現代化重構，不再僅限於傳統功能分解，轉為以「利害關係人關注點 (Concerns)」為核心：
  • Stakeholders：客戶、架構師、開發者、資安稽核員。
  • Viewpoint (視點)：定義觀察系統的角度與建模約定。
  • View (視圖)：依視點描繪出來的具體架構表現。
🧭
現代視點體系 (Viewpoints)
標準擴充出更彈性的視點集合：
  • Context Viewpoint：系統與外圍邊界。
  • Composition Viewpoint：組件階層封裝。
  • Logical & Information：物件類別與資料模型。
  • Patterns Viewpoint：所採用的架構模式（MVC、狀態機等）。
  • State Dynamics：動態生命週期與狀態切換。
💡 實務選用建議： 課堂作業或中小型系統，1998 版的「10 大實體屬性 + 4 大視圖」清晰易寫；而大型複雜微服務或物件導向專案，則推薦採用 2009 版的多重視點體系。
CHAPTER 06 :: 實務對照

🎯 專案實務對照：以《K33p_1t_s1mpl3》為例

看理論不如看實例！第九組網頁文字解謎 RPG 如何依循 IEEE 1016 落地：
IEEE 1016 設計視圖 第九組 SDD 實作內容 解決的工程挑戰
分解視圖 (Decomposition) 劃分 parser.js、state.js、ui.js、errorHandler.js、audio.js 純前端 SPA 高度解耦，5 位組員清楚分工（NF-05）
相依與介面視圖 單次指令事件驅動流：parseCommand() ➔ updateState() ➔ LocalStorage 規範模組通訊合約，達成 0.1 秒極速同步響應（NF-01）
詳細設計 (演算法) 正則表達式語法匹配、多人指令嚴格遞增排序、符文房號連線判定 確保複雜劇情指令精準觸發，防止玩家無效輸入卡死
詳細設計 (資料設計) 制定 GameState 與 LocalStorage JSON 資料字典，加入 Schema 防損毀保護 無伺服器下保障本機存檔可靠性與玩家隱私（NF-06, NF-08）
CHAPTER 07 :: 撰寫守則

💡 SDD 撰寫的三大黃金原則與避坑指南

✅
推薦做法 (Best Practices)
  • 適度抽象 (Right Abstraction)：專注於介面協定、資料結構與演算法流程，而非整篇貼上 JavaScript 原始碼。
  • 雙向追溯 (Traceability)：每個模組必須標註支援的 SRS 功能需求條目（如 F-01）。
  • 明確標記未定事項：若與 SRS 有出入或尚待確認（如彩蛋指令），明確在附錄列出。
❌
常見地雷 (Common Pitfalls)
  • 把 SDD 當成程式碼貼上簿：貼滿未抽象的語法，導致規格一改整份文件作廢。
  • 遺漏相依性說明：只畫了方塊圖，卻沒寫各方塊如何傳遞參數與處理錯誤。
  • 脫離 SRS 幻想架構：設計了 SRS 根本不需要的複雜微服務或額外後端。
CHAPTER 08 :: 步驟實踐

🐾 新手也能上手的 SDD 五步撰寫指引

STEP 1. 劃定範疇
明確系統邊界、技術棧（Tech Stack）與不在範圍內的項目（Out of Scope）。
STEP 2. 模組切分
繪製分解視圖，將系統拆解為數個獨立實體，並分配給組員認領責任。
STEP 3. 定義介面
規範函式名稱、輸入參數、回傳值格式與例外錯誤代碼（介面視圖）。
STEP 4. 資料字典與演算法
設計核心資料庫 / JSON 儲存模型，並撰寫關鍵邏輯虛擬碼（詳細設計視圖）。
STEP 5. 繪製追溯矩陣 (RTM)
交叉檢查 SRS 每一條需求是否有對應模組負責，確保 100% 需求不漏接！
