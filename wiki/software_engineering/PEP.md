# 專案執行計畫書 (Project Execution Plan, PEP)

## 摘要
專案執行計畫書（PEP）是軟體專案啟動時的指導性管理文件，明確界定專案目的、範疇邊界、人員職責、溝通機制、技術架構、里程碑時程與風險防範策略。本頁以《K33p_1t_s1mpl3》專案執行計畫書為基礎，歸納軟體工程專案執行計畫的核心架構與實務要點。

## 核心概念

### 1. PEP 的六大核心組成
根據軟體專案實務標準，一份完整的 PEP 涵蓋：
1. **專案目的與目標**：界定學術目的、產品願景及現實限制。
2. **專案範疇與功能系統**：定義核心功能、世界觀、敘事架構與邊界。
3. **人員分工與溝通計畫**：明確每位成員職責、協作流程與溝通管道。
4. **技術架構與開發工具**：設定技術棧（Tech Stack）與三層邏輯架構。
5. **多階段時程規劃 (Milestones)**：建立具體交付時間節點。
6. **品質保證與風險控管**：評估技術、體驗與協作風險，並制定驗收標準。

### 2. 目的三角形：學術、產品與限制
以《K33p_1t_s1mpl3》為例，PEP 透過三維度聚焦專案可行性：
- **學術面**：落實團隊協作與軟體工程流程，由架構單純的系統著手跑順完整生命週期。
- **產品面**：打造具創意與特色風格的作品（如結合 CTF 終端機指令解謎與心理驚悚敘事）。
- **限制面**：在有限開發週期（16 週）內，透過限縮範疇（指令式純前端，捨棄複雜繪圖與 3D 渲染）確保產出完整可交付。

## 詳細說明

### 1. 16 週軟體專案時程劃分（五大階段）
專案時程以階段性里程碑進行管理（參見 `se_pep_team_2026.pdf` 第五章）：
- **W1-W4（第一階段：需求與計畫擬定）**：核心發想、劇本定案、可行性評估、建立 GitHub Repository。**里程碑：10/8 PEP 完成**。
- **W5-W7（第二階段：系統分析與規格）**：繪製 Use Case 圖與流程圖、指令詞彙表、Terminal 雛形搭建。**里程碑：10/29 SRS 完成**。
- **W8-W10（第三階段：設計與核心實作）**：系統架構設計 (Architecture)、打字機特效、劇本轉譯 JSON。**里程碑：11/19 SDD 完成**。
- **W11-W15（第四階段：開發與品質保證）**：指令防呆測試、音效整合、STD 測試文件、撰寫使用手冊 (User Manual)、部署 GitHub Pages。**里程碑：12/24 STD 完成**。
- **W16（第五階段：收尾與展示）**：專題最終 Demo。

### 2. 人員分工與溝通規範
- **職責矩陣**：劃分口頭報告組與文件開發組。例如主程式由單一負責人（王文伶）編寫輸入解析器與狀態機；劇本由專人（杜汯溱）統籌並負責各階段成果檢核；介面與樣式（余苡萱）、線稿視覺（吳千心）、UI/UX 排版（王瑀彤）各有專職。
- **協作四要素**：
  1. *版本管制*：GitHub 控管程式碼與 GitHub Pages 部署。
  2. *定期會議*：每週 Google Meet 線上進度同步。
  3. *即時通訊*：LINE 專案群組處理突發與日常回報。
  4. *文件協作*：Google Docs 統整會議記錄與規格草稿。

### 3. 風險評估與因應策略
| 風險情境 | 潛在衝擊 | 因應策略（PEP 明確規範） |
|---|---|---|
| 玩家輸入無效指令導致卡關 | 遊戲體驗中斷 | 提供 `simple` 提示指令，並以引號/高亮標記互動關鍵字 |
| 文字量過大引發玩家疲勞 | 閱讀專注度下降 | 精簡單次輸出字數，控制打字機節奏，轉折處加入關鍵音效 |
| 跨組支援造成責任歸屬模糊 | 進度落後或權責不清 | 指定單一負責人（杜汯溱）擔任最終檢核者，追蹤交付物 |

## 注意事項與限制
1. **時程與資源嚴格性**：PEP 為前期承諾文件，若後續規格（SRS）大幅擴充，須重新評估 16 週里程碑是否受影響。
2. **去識別化與隱私考量**：在公開或共享 PEP 時，應確認團隊成員學號與個人資訊之授權狀態。
